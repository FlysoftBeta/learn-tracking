# 信息架构与维护决策

## 三层职责

| 层 | 位置 | 回答的问题 | 更新策略 |
| --- | --- | --- | --- |
| 用户阅读层 | `TASKS.md`、`journal/`、`notes/` | 我现在要做什么、我当时怎么想、我知道什么？ | 任务状态单一维护；笔记保留理解演变 |
| 检索层 | `index/`、标题、别名、相对链接 | 应该去哪里找、它还和什么有关？ | 随相关记录更新，尽量只存指针 |
| 证据层 | `sources/` | 这是谁说的、原文是什么、如何核对？ | 原文留存，提取文本单列，派生内容可追溯 |

`AGENTS.md` 是执行入口；本文件解释维护取舍；`PREFERENCES.md` 只记录明确偏好。Git 保存变更历史，但关键的“为什么改变理解”仍写入正文，避免只能靠日志找回。

## 捕获到物化

1. 捕获：保存有价值的用户原话或实际取得的资料，注明来源；一份输入可支持多个笔记，不重复复制证据。
2. 路由：任务进 TASKS；有独立主题的理解或想法直接进 notes；当天碎片进 journal。没有价值的空章节不用创建。
3. 关联：搜索同主题笔记。能融入就更新正文；新观点与旧观点冲突时写明日期、差异和来源，不假装已形成统一结论。
4. 物化：将值得复用的碎片提炼为可读笔记，保留原话链接及用户/agent 的观点边界。原始资料保持可追溯。
5. 发现：独立笔记加入主题地图；不要把每条日记、每个证据片段都重复列入总索引。
6. 持久化：按照 AGENTS.md 的 Git 工作流立即提交并推送。

“记一个想法”通常只需要一个证据文件、一篇想法笔记和一个索引入口，不必同时生成日记、项目计划、复盘和多个索引。补充同一想法通常只更新原笔记并追加来源。

## 单一事实来源

- 任务：同一事项保留同一 ID；计划日期、截止日期、状态仅在任务正文编辑。转化自想法时建立链接，不把原想法改写成承诺。
- 理解：笔记的“当前理解”是当前表述；“理解演变”保留重要转折；证据保存当时原话。
- 资料：原件和获取说明是证据；OCR、摘要、索引是派生内容。派生内容不能覆盖证据。
- 同名词不一定同一主题；同一主题也可能有多个别名。合并前对照语境。

## 日期与规模

日期采用 `YYYY-MM-DD`。明确区分事件时间、记录时间、计划日期和截止日期。“今天/明天”依据用户明确时区，否则使用环境时区并记录依据。用户时间表达与环境冲突且影响安排时先澄清。

默认全文搜索加链接即可。只有出现实际查找困难时再增加主题导航；只有长文难以阅读时再拆分；只有已结束任务影响阅读时才按年份归档。归档后的 ID 不变，旧链接和索引同步修复。不预建数据库、向量库、复杂标签体系或定时自动整理。

## 按需回顾

用户要求回顾或整理时，列出相关未完成事项、尚待澄清片段和理解变化，并提供正文链接。不要自动把积压任务搬到今天，不替用户取消任务，不把长期想法强行变成目标。

检查范围只覆盖本次修改：来源是否真实、主观表述是否保留、任务是否重复、相对链接是否有效、索引是否能找到新笔记、Git 是否实际同步。
