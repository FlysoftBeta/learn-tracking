# 信息架构

## 时间事实与检索视图

journal 是按时间组织的事实主线，记录用户当时的报告、理解、决定与实质变化。它不是逐字聊天备份，也不把个人理解认定为客观真理。

notes 是面向问题和主题的物化视图：由 journal 中的有效信息整理出当前需求、理解、方法和想法。允许压缩、重写和去除过时表述；历史由 journal 承担。TASKS 是任务当前状态的专用视图，只有这里编辑状态。journal 中的任务事件用于追溯，不是另一份待办清单。

index 只提供主题入口和有用别名。sources 保存需要保留的原件、精确引文和提取文本，按需核对，不是默认上下文。

## 输入到记忆

1. 理解：修复明显 typo、重复和明确省略，提取真实意图；实质歧义才澄清。
2. 记事：在事件日期的 journal 追加简洁语义记录；补记时注明记录日期。相同消息重试不重复创建事件。
3. 物化：有持久增量才更新 notes、TASKS 或偏好。优先融入已有正文，链接相关 journal 小节。
4. 索引：只在出现新主题、位置或用途变化时更新入口。
5. 持久化：快速审阅本次变更，立即 commit、push。

普通对话记录一般不必新建 sources 文件；journal 的语义事件足以承载出处，需要逐字核对时才保留原话。外部文档和附件可保存原件，派生笔记写清来源及验证范围。

## 进入 notes 的门槛

每段应能回答一个未来有用的问题。例如项目的需求、知识的解释模型、一个值得发展的想法、解题的关键推导或有启发性的失败原因。成熟度不是门槛，持久用途才是。

拼写修复、对话修补、已消除的措辞疑问、重复复述、agent 的维护过程不进入 notes。不要为了“保留演变”复制全部历史；只有能解释当前理解的实质转折值得留下。

修正表达不等于改变想法。前者直接修正文案，后者在 journal 追加实际变化和原因，然后更新当前视图。原始引文不改写。既有低价值过程段落可以从 notes 删除，真实历史仍可在 journal、原始来源和 Git 中追溯。

## 项目分类

项目是内容归属边界。学习app 的布局、前端和工程需求维护在 notes/学习app/；本仓库的信息架构、记录工作流及检索质量维护在 notes/外置记忆项目/。同日 journal 可以容纳多个项目，但各事件标题必须带项目名，并保持发生顺序。

主题页保持本项目范围；跨项目联系仅以链接表达。外置记忆项目页提供规范文档入口，具体执行规则仍在 AGENTS.md 等权威文档中单处维护。

## 检索与规模

当前主题：index → 相关 notes 小节。任务安排：TASKS。历史和变化：对应 journal。逐字核对：相关 sources。根据问题选择路径，不默认把所有层一起读入上下文。

先搜索定位再读取，优先高相关片段；别名不收录误拼。查不到时扩展同义词及相关时间范围，说明实际检索范围，不编造记忆。派生视图与 journal 不一致时核对时间与语义，修复视图。

目录按内容增长，不强制迁移现有主题目录。只有真实检索困难时增加主题导航，只有长文难读时拆分。归档保持 ID 和链接有效；不自动搬运积压任务或制造定期复盘。

## 日期与状态

日期采用 YYYY-MM-DD。区分事件日期、记录日期、计划日期和截止日期；使用用户明确时区，否则使用环境时区。可能影响安排的歧义才询问。不得添加用户没有承诺的日期、任务或完成状态。
